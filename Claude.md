# ferrocache — Project Context

## Section 1: Evergreen

**What this is:** Distributed semantic cache for LLM applications, written in Rust. Single binary, multi-node via consistent hashing + gossip replication. Portfolio project for big-tech Core SWE interviews.

**Current phase:** Phase 7 in progress. M27 done (exact-match pre-filter). Next: M28 — cache scope + tenant isolation.

**Architecture decisions (append-only, one line each):**
- Client computes embeddings externally; ferrocache stores/compares f32 vectors
- Crates: tokio, axum 0.7, hnsw_rs, chitchat 0.10, tracing, serde_json, config, reqwest
- WAL format: newline-delimited JSON, replayed on startup, fsync per insert
- Consistent hashing key: u64 from first 8 bytes of embedding (first 2 f32 values, big-endian)
- Cosine distance: hnsw_rs DistCosine returns 1-similarity; we convert
- Side-table: HashMap<usize, CacheEntry> keyed by hnsw internal id; UUID inside CacheEntry
- WAL is source of truth; production insert path is WAL-first then replay_entry
- insert() (UUID-generating) is #[cfg(test)] only; production uses replay_entry
- Config priority: env vars (FERROCACHE_ prefix, `_` prefix-sep, `__` section-sep, `,` list-sep) > ferrocache.toml > defaults
- tokio::sync::RwLock for index; WAL is owned by a single background flush task (no shared mutex)
- Validation limits (server.rs constants): MAX_EMBEDDING_DIM=4096, MAX_RESPONSE_BYTES=102_400
- Threshold accepted range on /query: 0.0..=1.0
- Hash ring: FNV-1a (cross-process deterministic), 64 virtual nodes per physical node by default
- Cluster mode is opt-in via `cluster.enabled`; `false` keeps Phase 1 behavior bit-identical
- Ring reconciler runs every 2s in a background task; chitchat gossip interval = 1s
- Each node advertises its API addr via chitchat KV under key `api_addr`; reconciler reads peers' addrs
- Routing: `?local=true` skips ring lookup (used by forwarded requests + debugging); coordinator stamps UUID before fan-out
- Replication: synchronous, primary-or-coordinator + (replication_factor-1) replicas; any replica failure → 502
- Forward failures return 502 (BAD_GATEWAY) to distinguish "peer failed" from local 500
- Docker runtime image needs `libgomp1` (hnsw_rs → rayon → OpenMP)
- `seed_nodes` is parsed from a comma-separated env string via config-rs `list_separator(",")`+`with_list_parse_key`
- `Wal::open` mkdir's parent dir so containers can mount an empty `/data` volume
- Crate is library + binary (lib.rs re-exports modules); `cargo build --release --bin ferrocache` for prod images
- Benchmarks via criterion; Python client uses only stdlib (urllib+json)
- Python package on PyPI with optional extras; Docker image on GHCR; release CI on version tags
- Index is namespace-partitioned by `model_id`; each namespace has its own HNSW instance + side-table
- `model_id` is required on `/insert` and `/query`; old WAL entries without it default to `legacy::unknown`
- `model_id` format convention: `model_name::dimension` (e.g. `all-MiniLM-L6-v2::384`)
- Cross-namespace queries are impossible by construction — vectors from different models never compare
- Snapshot format: `magic (FERROSNA) + version (u64=1) + wal_sequence (u64) + entry_count (u64) + bincode-encoded Vec<SnapshotEntry>`; written atomically via temp+rename so a crash never corrupts the prior snapshot
- Compaction: snapshot the side-table entries, then truncate the WAL — HNSW is rebuilt from stored embeddings on load (no need to serialize the graph itself)
- WAL entries carry a monotonic `sequence: u64` that never resets — startup skips entries `<= snapshot_watermark` so the WAL tail replay is bounded
- Auto-compaction every N inserts (default 10K via `compact_interval_inserts`, 0 disables); manual via `POST /admin/compact`
- `CacheEntry` again stores `embedding` + `query_text` so snapshots can dump the full record (re-added in M15; was dropped in M4)
- Prometheus `/metrics` is hand-written (no `prometheus`/`metrics` crate); atomic counters with `Ordering::Relaxed` + a fixed-bucket `LatencyHistogram`
- Per-namespace hit/miss/insert counters carry a `namespace` label; global query/insert latency histograms have 16 buckets (100µs → 10s) plus a `+Inf` bucket
- `/stats` JSON gained a `counters` object so users without Prometheus can still read the same numbers
- Monitoring stack lives in `monitoring/` as a docker-compose overlay (`-f docker-compose.yml -f monitoring/docker-compose.monitoring.yml`); base cluster runs unchanged without it
- `CacheEntry` again stores `embedding` + `query_text` so snapshots can dump the full record (re-added in M15; was dropped in M4)
- Bearer token auth via `FERROCACHE_AUTH_TOKEN` env var; disabled when unset (opt-in, backward compatible)
- Auth exempts `/health` and `/metrics` (load balancers and Prometheus need unauthenticated access)
- Token comparison uses `subtle::ConstantTimeEq` to prevent timing attacks; the token value is never logged at any level
- Inter-node replication forwards include the same bearer token (shared-secret cluster model — all nodes carry the same `FERROCACHE_AUTH_TOKEN`)
- mTLS between cluster nodes via rustls 0.23 + rcgen 0.13; opt-in via `cluster.tls.enabled`; second TLS listener on `internal_port` (default `port + 1000`) serves the same router; public port stays plain HTTP
- Dev mode (no cert paths) auto-generates a self-signed CA + leaf in memory; production loads PEMs from `cluster.tls.{ca_cert,node_cert,node_key}_path`
- TLS reqwest client trusts ONLY the cluster CA (system roots disabled) and presents the node leaf as client identity — i.e. mTLS, not just TLS
- Gossip (chitchat UDP) remains unencrypted: it carries only ring metadata (node IDs + forwarding addresses), not cached data
- `cargo run --bin gen_certs [node_ids...]` writes `./certs/ca.pem` + `./certs/<node>/{cert,key}.pem` for local clusters; the production Dockerfile builds only `--bin ferrocache`, so `gen_certs` never ships in images
- Replication retry: exponential backoff (50ms × 2^attempt, ±20% jitter, capped at 5s), max 3 attempts by default; retries on connect errors + timeouts + 5xx only, never on 4xx (deterministic failures)
- `ferrocache_replication_retries_total` metric tracks retry pressure separately from final failures — retries that succeed do NOT count as failures, so dashboards can distinguish "noisy network, eventually succeeded" from "peer permanently down"
- WAL group-commit (M20): inserts push `WalCommand::Insert` to an mpsc channel; a single background flush task owns the `Wal`, batches up to `wal_batch_size` requests (default 256) or `wal_batch_timeout_ms` (default 1ms) elapses, writes the entire batch in one `write(2)` and one `fsync(2)`, then takes the index write lock once and inserts every entry; per-request oneshot replies fire after the lock is released. `wal_batch_size = 1` degrades to per-insert fsync (pre-M20 behavior) and is what tests use.
- Insert throughput scales with concurrency under group-commit (measured: 7.5× at concurrency 100 vs per-insert fsync); single-client insert is slightly slower (batch timeout adds ~1ms wait); query throughput is unaffected (read path doesn't fsync)
- The flush task is the SOLE writer to the WAL — `compact` is also a `WalCommand` so it serializes with insert flushes (FIFO via the same channel); auto-compaction's `inserts_since_compact` counter lives in the flush task only (no atomics, no locking, single producer)
- Insert handler error surface: `InsertError::Wal` → 500 "persistence failed" (paths/error chain stay in logs), `InsertError::Index` → 500 with the underlying message (e.g. "dimension mismatch") preserving M19 audit shape
- Phi accrual failure detector per peer: sliding window of heartbeat inter-arrivals (default 100 samples), normal CDF, phi = -log10(1-F(elapsed)); threshold 8.0 default (Cassandra/Akka standard); std-dev floored at 100ms so a perfectly regular heartbeat stream still has a defined CDF
- Heartbeats piggybacked on chitchat gossip — the existing 2s reconciler tick records a heartbeat for each peer chitchat reports as live, then runs `check_all`; no separate heartbeat task
- Three peer states: `Alive → Suspected (phi ≥ threshold) → Dead (phi ≥ 2×threshold)`; recovery to `Alive` on any new heartbeat (Dead is not permanent — ring removal is M22's job)
- Dead peers skipped in query routing (immediate miss instead of retry-then-502) and insert fan-out (degraded replication with warn log naming `dead_peers` and `effective_replicas`); soft optimization, retry logic still runs if a "dead" peer races back into a request
- Per-peer phi exposed as `ferrocache_peer_phi{peer=...}` gauge plus `ferrocache_peers_suspected` / `ferrocache_peers_dead` gauges in /metrics; `peer_health` map in /cluster/status JSON
- Ring membership decoupled from chitchat liveness (M22): ring removals driven exclusively by phi accrual `Dead` status; `Suspected` peers stay in the ring (might recover); `chitchat.live_nodes()` controls discovery + KV propagation only
- Dead nodes tracked in `dead_nodes: HashSet<String>` on `ClusterState`, surfaced via `/cluster/status.dead_nodes`; re-joining nodes (reappear in chitchat snapshot) are added back to ring AND removed from the dead set on the same reconcile tick
- Ring reassignment is automatic and zero-data-movement: removing a dead node's virtual nodes from the `BTreeMap`-backed `HashRing` makes its arc fold into the clockwise successor, which is already a replica thanks to `replication_factor=2` — the cache property (no durable single-source-of-truth contract) means we don't need anti-entropy to ship data; missed entries are recomputed by the LLM on the next miss
- `failure_detector.remove_peer` is NOT called from the reconciler — the detector keeps history across chitchat-driven drops so phi can keep climbing into Dead even after gossip stops reporting the peer; only when an operator actually removes a node from the cluster would `remove_peer` apply (out of scope)
- Re-joined nodes serve stale data until the next anti-entropy pass (M23 will add this); stale misses are acceptable in cache semantics — the client re-calls the LLM, the response is cached on the new owner, ring is consistent again
- `dead_node_removal_enabled` config flag (default `true`) supports a monitoring-only mode where phi reports without ring mutation — useful for canary rollouts of the failover behaviour
- Ring change observability: `ferrocache_ring_changes_total` counter (every add or remove from the reconciler) + `ferrocache_ring_members` gauge mirror what's in the ring; bumped from `Metrics::record_ring_change()` inside `reconcile_step`
- Read repair on query miss (M23): coordinator (= ring owner that received the forwarded query) queries non-dead replicas in parallel via `futures::future::join_all`, returns first hit to client immediately, spawns `tokio::spawn` background task that fetches full entry via `/internal/entry/{uuid}` then re-inserts locally through the WAL group-commit channel (full durability); failures (network, 404, channel closed) increment `read_repair_failures_total` but never crash
- `/internal/entry/{uuid}` returns `FullEntryResponse { uuid, embedding, response, query_text, model_id }` — embedding is required so the coordinator can re-insert; 404 maps to `Ok(None)` in `forward_get_entry`; `/internal/read-repair` is a UUID-mandatory `/insert` variant going through the same WAL channel
- `LocalParam.repair: Option<bool>` semantics: `None` defaults to "repair if NOT explicitly local-only" (so client `?local=true` skips repair, but the coordinator's forwarded `?local=true&repair=true` triggers it); `Some(false)` set by the read-repair fan-out itself prevents recursion; `Some(true)` set by the coordinator's `forward_query` makes the recipient know it's the canonical primary
- UUID reverse lookup populated on every `replay_entry`/`replay_snapshot_entry` (not just new inserts) — old WAL/snapshot replay paths also benefit from O(1) uuid lookup
- Read repair is eventually consistent — re-joined nodes heal as traffic naturally queries their stale arcs; entries never queried again are never repaired (acceptable for a cache, since a forgotten entry just means the LLM gets called again on its next visit)
- No Merkle trees, no background reconciliation, no bulk transfer — read repair only, one entry at a time. Phase 6 spec deliberately picked this over the more complex Cassandra-style anti-entropy because the cache semantics make eventual healing through traffic perfectly correct.
- `read_repair_enabled` config flag (default `true`) gates the entire fan-out — when false, a coordinator miss returns immediately without touching replicas; phi monitoring still runs
- `CacheEntry` tracks `inserted_at` (set once, persisted in WAL), `last_accessed_at` (updated in-memory on every hit, persisted in snapshots), `access_count` (same)
- Access metadata is soft state: WAL stores only `inserted_at`; `last_accessed_at` and `access_count` are snapshot-persisted but lost on crash (rebuild naturally via traffic) — the alternative (a WAL write per query hit) would defeat the cache
- Query hits take a brief index write lock for metadata update (HashMap lookup + 2 field writes, sub-µs); misses stay read-only
- `/admin/entry-stats` exposes top-10 most-accessed entries per namespace for ops visibility — O(n log n) sort per namespace, fine for an admin endpoint
- `QueryHit` carries `internal_id: usize` so the handler can call `record_access` without a second HNSW or HashMap lookup
- Pre-M24 WAL entries lack `inserted_at` and deserialize to 0; pre-M24 snapshots default the three new fields to 0 via `#[serde(default)]` — entries with `inserted_at == 0` are treated as "oldest" by future LRU (M25), the correct behaviour for entries from before access tracking
- LRU eviction via `max_entries_per_namespace` (default unlimited): on overflow, evict the entry with smallest `last_accessed_at`; O(n) scan per eviction (acceptable at cache scale)
- LRU tie-break order: `(last_accessed_at, inserted_at, internal_id)` — when timestamps tie (sub-second insert burst), the smaller internal id evicts first, giving deterministic FIFO-on-tie behaviour matching "oldest entry first"
- HNSW lazy deletion: evicted internal IDs tracked in `evicted_ids: HashSet<usize>`; query results filter against it before threshold check; search requests `1 + evicted.len().min(8)` extra candidates to compensate
- HNSW rebuild triggered when `evicted_ids.len() / (entries.len() + evicted_ids.len()) > 0.20`; rebuilds from scratch using only live entries; runs inline in the flush task under the write lock
- WAL tombstones: `{"tombstone":true,"uuid":"...","model_id":"...","sequence":N}` — on replay, remove the entry instead of inserting; `embedding`/`response`/`query_text` empty/default; prevents evicted entries from returning after restart
- Snapshots exclude evicted entries by construction (side-table only has live data); tombstones in the WAL tail override snapshot entries on replay
- Eviction runs inline in the flush task after each insert batch; the index write lock is acquired once, eviction + rebuild + tombstone collection happen under it, then the lock drops and tombstones are written as a single fsync — eviction is a soft cap (may briefly exceed by `batch_size` entries)
- TTL via `ttl_seconds` on insert → `expires_at = inserted_at + ttl` stored in WAL/snapshot; expired entries return miss on query (checked inline, no state mutation); background reaper cleans up + writes tombstones
- Background expiry reaper runs every `expire_scan_interval_secs` (default 60s; 0 disables); scans all namespaces under write lock, evicts expired entries, writes tombstones through the WAL channel one by one (flush task batches them); startup does one `collect_expired` pass before binding the listener
- `DELETE /entry/:uuid` removes from index + writes tombstone + fans out to all live peers (NOT ring-based — UUID has no embedding to hash); 404 from a peer is idempotent success
- `POST /admin/invalidate` finds entries with cosine sim ≥ threshold via O(n) side-table scan + evicts + tombstones + fans out to replicas (each replica computes its own matches with the same `(embedding, threshold)` — no UUID list shipped, contract is "compute, not copy")
- Three invalidation metrics with the same per-namespace + global pattern as M25 evictions: `expirations_total` (TTL), `deletions_total` (explicit DELETE), `invalidations_total` (semantic radius)
- The reaper task is a separate `tokio::spawn`, NOT part of the flush task — separation of concerns; the flush task stays the sole WAL writer, the reaper sends tombstones through the WAL channel like any other producer
- Exact-match pre-filter (M27): `HashMap<normalized_query_text, uuid>` per namespace, checked BEFORE HNSW ANN search when `query_text` is present on `/query`; O(1) vs O(log n) for HNSW. Hit reports `similarity: 1.0` and `exact_match: true`; ANN hits report `exact_match: false`; misses omit the field entirely
- Text normalization: `text.split_whitespace().map(str::to_lowercase).join(" ")` — lowercase + trim + whitespace-collapse. No stemming, no Unicode normalization (NFKD etc.) so behaviour stays predictable
- Single removal helper `NamespacedIndex::drop_entry(internal_id)` is the SOLE point that mutates the side-table on removal — every public path (`evict_lru`, `remove_by_uuid`, `remove_internal`, `collect_expired_within`) funnels through it, so exact-match cleanup never gets forgotten
- Exact-match cleanup uses a UUID ownership check: only remove the key when its current value still references the dropped UUID — protects against a delete-then-reinsert losing the new entry's mapping
- HNSW rebuild does NOT touch `exact_match_index`: UUIDs are stable across rebuild, so the existing mappings remain correct
- Python middleware + LangChain + LlamaIndex + MCP all forward `query_text` to `client.query()` automatically — no explicit caller change needed for the exact-match pre-filter to fire
- `ferrocache_exact_match_hits_total` is ADDITIVE to `ferrocache_queries_hit` — every exact-match is also a regular hit, the new counter is a subcategory not an alternative

**Key decisions:**
- **Inline expiry check, no state mutation in query path.** The brief weighed both options and picked Option A. Mutating `evicted_ids` from the query path would require a write lock on every hit-against-expired-entry, which inverts the M24 read-lock optimisation. The reaper's eventual cleanup is fine because the inline check guarantees correctness — a stale entry NEVER gets returned. The "ghost in HNSW until reaper runs" period is bounded by `expire_scan_interval_secs`, which is operator-controlled.
- **Reaper uses the existing WAL channel, not a new `WalCommand::WriteTombstones(Vec<...>)`.** The brief preferred the simpler approach. Each tombstone goes through `WalCommand::Insert { entry: tombstone, respond: oneshot }`, which the flush task already knows how to write. Group-commit batching means N tombstones become one fsync — same outcome as a bulk variant, less code.
- **DELETE fans out to ALL peers, not just ring replicas.** With `replication_factor=2` and a 4-node cluster, each entry exists on 2 of 4 nodes — but the DELETE handler doesn't have the embedding to know which 2. Sending to all 4 is O(N), trivially small for an admin operation. 404 from peers that don't have the entry is harmless (idempotent). The alternative — somehow looking up the embedding first to hash it — adds a HEAD-like fetch round-trip and breaks the simple "delete is a write, not a read+write" semantic.
- **Invalidate ships embedding + threshold, not the UUID list.** The brief explicitly chose this. Each replica computes its own match set against `(embedding, threshold)`. If replicas are in sync, every replica produces the same UUID list. If they're NOT in sync (a replica is stale because of M22/M23 race), shipping the UUID list would over- or under-invalidate; computing locally is the safe degenerate behaviour. The cost: one extra O(n) scan per replica, but `/admin/invalidate` is admin-tier so this is fine.
- **Standalone `cosine_similarity` instead of reusing `DistCosine`.** `hnsw_rs::DistCosine` returns "1 - similarity" via a private code path; reusing it would mean either (a) running the HNSW search in radius mode (which the API doesn't support natively) or (b) constructing fake `Distance` instances. A 5-line standalone function is clearer, testable in isolation, and handles edge cases (zero vectors, mismatched dims) explicitly.
- **`ttl_seconds = None` is the default.** All existing tests pass unchanged; pre-M26 WAL/snapshot entries deserialize to `None` via `#[serde(default)]`. No migration step needed.
- **Startup expiry pass runs BEFORE the listener binds.** A long-downtime restart (server off for an hour, entries with `ttl_seconds=300`) would otherwise serve up to 12 expired entries before the first reaper tick. The startup pass eliminates that window. The tombstones for the startup pass are written AFTER the flush task spawns (before the listener), so they're durable before the first request lands.
- **`now_unix_secs()` cached once per query call.** Calling `now_unix_secs()` per neighbour in the loop would race the wall clock between candidates. Pre-computing once means all candidates evaluate against the same instant — deterministic.
- **Empty-uuid 400 on DELETE.** axum's `:uuid` route param happily matches the empty path segment in some routing configurations, so the handler explicitly checks `uuid.trim().is_empty()` and returns 400. Defensive but cheap.
- **Reaper task is spawned independently of the flush task.** Same separation-of-concerns argument as M25's "rebuild lives in the flush task" decision but inverted: rebuild is tightly coupled to inserts (the trigger ratio depends on inserts driving evictions), so it lives in the flush loop. Expiry is tightly coupled to wall-clock time, so it lives in its own ticker. Two tasks, each driven by a clear signal.

**Open / next:**
- **Reaper's "first tick" timing.** `tokio::time::interval(d)` fires the first tick immediately. We `ticker.tick().await` once before the loop to skip that first tick (startup already did one expiry pass). The next tick comes `interval` seconds later. So with `expire_scan_interval_secs=60`, the worst-case latency for an expired entry to be reaped is ~60s — acceptable, matches the operator-set knob.
- **Cluster invalidate compute-on-each-replica is slightly wasteful.** Each replica does its own O(n) scan. For replication_factor=2 and a 100K-entry namespace, that's ~200K total cosine ops per invalidate call. Not a hot path, fine. Future optimisation: ship a digest of the matched UUIDs and let replicas verify via UUID lookup — but that requires every replica to have all relevant UUIDs, which isn't guaranteed under read-repair semantics.
- **DELETE response is "deleted: true" even on local-only paths where peers might still have it.** The local node's response reports its own success. If the cluster fan-out fails to reach a stale-but-alive peer, that peer still has the entry until it reads the WAL or gets the tombstone via gossip later. M26 doesn't add a gossip-based delete propagation; clusters with very stale peers might serve a deleted entry from one node for a while. Cluster integration tests don't currently catch this — would need a "kill node, delete via another node, restart killed node, query killed node" scenario. Out of scope for now.
- **Reaper failure modes are logged but never crash.** Channel-closed → log + continue. Flush-task-dropped-reply → log + still bump the metric. The trade-off: a missed reap just means the stale entry stays until the next tick. The alternative (panic + restart) would be louder but waste user requests.
- **`expires_at` is monotonic and absolute, not relative.** A clock skew across nodes means `now > expires_at` could fire at different wall-clock instants. For TTL semantics this is fine — we want "evict ~5 minutes after insert", not "evict at exact 12:34:56". For audit/compliance use cases (where exact-second deadlines matter), the operator would need to ensure NTP sync.
- **`POST /admin/invalidate` runs O(n) per namespace per replica.** For a 1M-entry namespace, that's ~10ms of f32 math at ~100K ops/ms, plus replication_factor times that across the cluster. For an admin operation triggered manually, this is fine. If invalidation became a hot path (e.g. driven by a content-change webhook), an HNSW-radius-search variant or a coarse pre-filter (by, say, query_text hash bucket) would be the next step.
- **Pre-M26 snapshots will fail to deserialize** — same bincode-positional issue as M24/M25. The "corrupt-snapshot → full WAL replay" fallback handles it.

The HNSW iteration already does this for M26's expiry check; the M27 pre-filter joins the same convention. Determinism: every candidate evaluates against the same instant.
- **Pre-filter result reports `similarity: 1.0`.** It IS exactly 1.0 by construction — the entry's stored `query_text` normalized to the same key as the lookup. The caller can distinguish the source via `exact_match: true`. Two information channels (similarity number + boolean), each independently meaningful.
- **Empty normalized text is not indexed.** A user inserting an entry with `query_text: "   "` would otherwise create the key `""` → uuid in the map. The next query with empty `query_text` (or a request that fell back to `Some("")` from a missing prompt) would falsely match. Skipping at insert time keeps the cache safe against this.
- **HNSW rebuild is unchanged.** UUIDs are stable across rebuild — only internal IDs change. `exact_match_index` keys (normalized text) and values (UUID) both remain valid. No clear, no rebuild — saves O(n) work on every M25 rebuild trigger.
- **Middleware/LangChain/LlamaIndex/MCP are silent participants.** Each path already had the user's prompt in scope (it's where the embedding comes from). Forwarding it as `query_text` is one line per call site, no public API change. The pre-filter "just works" for every existing integration without any caller-facing migration.
- **Metric is additive, not exclusive.** `ferrocache_exact_match_hits_total` counts a SUBSET of `ferrocache_queries_hit`. Operators can compute the pre-filter share as `exact_match_hits / queries_hit`. Making it exclusive (decrement queries_hit on exact-match) would have been confusing; the existing dashboards keep working untouched.
- **No WAL/snapshot schema change.** The exact-match index is fully derivable from `query_text` (which has been in the WAL since M3). Replay reconstructs it via `insert_with_uuid` going through the populate-on-insert path. Zero migration cost, zero on-disk format change.
- **No stemming, no Unicode normalization.** Brief was explicit. Predictable behaviour beats clever-but-locale-dependent matching. Operators who want fuzzier matching add a normalization layer client-side; the server's job is to give them O(1) lookup against whatever they send.

**Deviations:**
- Brief proposed `text.trim().to_lowercase().split_whitespace().collect::<Vec<_>>().join(" ")` for normalization. Implemented as `text.split_whitespace().map(str::to_lowercase).collect::<Vec<_>>().join(" ")` — same output for ASCII, slightly more efficient for inputs with significant leading/trailing whitespace (`split_whitespace` handles trim implicitly), and avoids one full string allocation.
- Brief sketched the cleanup as "if let Some(entry) = self.entries.remove(...)" with cleanup inline at every call site. Hoisted into `drop_entry` (see Key decisions above) — same outcome, half the code, single place to evolve.
- Brief had `QueryHit.exact_match` and `QueryResponse.exact_match` as separate concerns. Threaded the field on `QueryHit` straight into the response so the handler doesn't need a manual map. Single source of truth.
- Brief proposed a `test_exact_match_via_http` server test that just checks the field. Strengthened: ALSO verify `similarity: 1.0`, the UUID matches, and the embedding was deliberately orthogonal (would miss in HNSW) — proving the pre-filter actually short-circuits rather than being a fluke ANN hit.
- Brief had two separate Python tests for `delete_entry_method` and `delete_entry_includes_auth` from M26 + a single new test for `query_passes_query_text`. Bundled the M27 Python tests into a fresh `test_exact_match.py` (parallel to `test_deletion.py`) so the file structure stays small and easy to grep. Three tests there: `query_passes_query_text`, `query_omits_query_text_by_default`, `middleware_passes_query_text`.
- Brief's `test_middleware_passes_query_text` assumed `wrap_openai(client, cache=...)` accepts a `cache` kwarg. The actual `wrap_openai` factory builds its own `FerrocacheClient` from env. Used the underlying `WrappedOpenAIClient` class directly so the test can inject a mock cache. Same coverage, no public API change.
- Brief implied the exact-match index could store internal IDs directly. Used UUIDs because (a) UUIDs are stable across rebuild while internal IDs are not, (b) the ownership check only makes sense with UUIDs (internal IDs would already have been recycled by `next_id` after a rebuild), and (c) the lookup chain `text → uuid → internal_id` only adds one HashMap step, which is negligible.

**Open / next:**
- **Normalization is ASCII-centric.** `to_lowercase` for ASCII is correct; for some Unicode letters (German ß, Turkish dotted/dotless I) the result depends on locale conventions, which Rust's std intentionally doesn't bake in. For an LLM-prompt cache where most queries are English, this is fine. Operators who care can pre-normalize their `query_text` before insert/query.
- **No prefix or fuzzy matching.** Two queries that differ only by a typo bypass the pre-filter and go through HNSW (which is fine for small typos — the embedding usually still matches above threshold). M27 is "exact equality after light normalization", not "approximate text matching". A `levenshtein < N` extension would be straightforward but isn't requested.
- **Exact-match index doesn't show in `/admin/entry-stats`.** That endpoint reports the top-N most-accessed entries. The exact-match index size could be a useful operator gauge ("how many entries are pre-filterable") but isn't surfaced. Easy to add if asked.
- **No rate limit on exact-match lookups.** A naive attacker spamming `/query` with `query_text` to hammer the HashMap is theoretically possible. In practice the HashMap lookup is faster than even the bearer-token check, so this is a non-issue at any scale ferrocache targets.
- **Memory cost: ~`(text_size + uuid_size) × entries`.** For 100K entries with 64-char average prompts and 36-char UUIDs, that's ~10MB. Negligible at design scale; would need a strategy for 100M-entry deployments (none planned).
- **Pre-M27 snapshots/WAL replay correctly.** No new on-disk fields. Existing `query_text` in WAL/snapshot drives the rebuild. Pre-M27 binaries don't need the index, and post-M27 binaries reading pre-M27 snapshots populate it during replay via the existing insert path.
- **Cluster invalidate doesn't ship the exact-match index.** `find_similar` ignores it (the pre-filter doesn't help with similarity sweeps; it's a different lookup pattern). Operators clearing entries via `/admin/invalidate` get the side-effect cleanup for free because `invalidate_similar` calls `remove_internal` → `drop_entry` → exact-match cleanup. Verified by `test_exact_match_survives_multi_path_removal`.
