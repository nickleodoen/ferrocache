**Architecture decisions (append-only, one line each):**
- Client computes embeddings externally; ferrocache stores/compares f32 vectors
- Crates: tokio, axum 0.7, hnsw_rs, chitchat 0.10, tracing, serde_json, config, reqwest
- WAL format: newline-delimited JSON, replayed on startup, fsync per insert
- Consistent hashing key: u64 from first 8 bytes of embedding (first 2 f32 values, big-endian)
- Cosine distance: hnsw_rs DistCosine returns 1-similarity; we convert
- Side-table: HashMap<usize, CacheEntry> keyed by hnsw internal id; UUID inside CacheEntry
- WAL is source of truth; production insert path is WAL-first then replay_entry
- insert() (UUID-generating) is #[cfg(test)] only; production uses replay_entry
- Config priority: env vars (FERROCACHE_ prefix, `_` prefix-sep, `__` section-sep, `,` list-sep) > ferrocache.toml > defaults
- tokio::sync::RwLock for index, tokio::sync::Mutex for WAL
- Validation limits (server.rs constants): MAX_EMBEDDING_DIM=4096, MAX_RESPONSE_BYTES=102_400
- Threshold accepted range on /query: 0.0..=1.0
- Hash ring: FNV-1a (cross-process deterministic), 64 virtual nodes per physical node by default
- Cluster mode is opt-in via `cluster.enabled`; `false` keeps Phase 1 behavior bit-identical
- Ring reconciler runs every 2s in a background task; chitchat gossip interval = 1s
- Each node advertises its API addr via chitchat KV under key `api_addr`; reconciler reads peers' addrs
- Routing: `?local=true` skips ring lookup (used by forwarded requests + debugging); coordinator stamps UUID before fan-out
- Replication: synchronous, primary-or-coordinator + (replication_factor-1) replicas; any replica failure → 502
- Forward failures return 502 (BAD_GATEWAY) to distinguish "peer failed" from local 500
- Docker runtime image needs `libgomp1` (hnsw_rs → rayon → OpenMP)
- `seed_nodes` is parsed from a comma-separated env string via config-rs `list_separator(",")`+`with_list_parse_key`
- `Wal::open` mkdir's parent dir so containers can mount an empty `/data` volume
- Crate is library + binary (lib.rs re-exports modules); `cargo build --release --bin ferrocache` for prod images
- Benchmarks via criterion; Python client uses only stdlib (urllib+json)
- Python package on PyPI with optional extras; Docker image on GHCR; release CI on version tags
- Index is namespace-partitioned by `model_id`; each namespace has its own HNSW instance + side-table
- `model_id` is required on `/insert` and `/query`; old WAL entries without it default to `legacy::unknown`
- `model_id` format convention: `model_name::dimension` (e.g. `all-MiniLM-L6-v2::384`)
- Cross-namespace queries are impossible by construction — vectors from different models never compare
- Snapshot format: `magic (FERROSNA) + version (u64=1) + wal_sequence (u64) + entry_count (u64) + bincode-encoded Vec<SnapshotEntry>`; written atomically via temp+rename so a crash never corrupts the prior snapshot
- Compaction: snapshot the side-table entries, then truncate the WAL — HNSW is rebuilt from stored embeddings on load (no need to serialize the graph itself)
- WAL entries carry a monotonic `sequence: u64` that never resets — startup skips entries `<= snapshot_watermark` so the WAL tail replay is bounded
- Auto-compaction every N inserts (default 10K via `compact_interval_inserts`, 0 disables); manual via `POST /admin/compact`
- `CacheEntry` again stores `embedding` + `query_text` so snapshots can dump the full record (re-added in M15; was dropped in M4)
- Prometheus `/metrics` is hand-written (no `prometheus`/`metrics` crate); atomic counters with `Ordering::Relaxed` + a fixed-bucket `LatencyHistogram`
- Per-namespace hit/miss/insert counters carry a `namespace` label; global query/insert latency histograms have 16 buckets (100µs → 10s) plus a `+Inf` bucket
- `/stats` JSON gained a `counters` object so users without Prometheus can still read the same numbers
- Monitoring stack lives in `monitoring/` as a docker-compose overlay (`-f docker-compose.yml -f monitoring/docker-compose.monitoring.yml`); base cluster runs unchanged without it
- `CacheEntry` again stores `embedding` + `query_text` so snapshots can dump the full record (re-added in M15; was dropped in M4)
- Bearer token auth via `FERROCACHE_AUTH_TOKEN` env var; disabled when unset (opt-in, backward compatible)
- Auth exempts `/health` and `/metrics` (load balancers and Prometheus need unauthenticated access)
- Token comparison uses `subtle::ConstantTimeEq` to prevent timing attacks; the token value is never logged at any level
- Inter-node replication forwards include the same bearer token (shared-secret cluster model — all nodes carry the same `FERROCACHE_AUTH_TOKEN`)
- mTLS between cluster nodes via rustls 0.23 + rcgen 0.13; opt-in via `cluster.tls.enabled`; second TLS listener on `internal_port` (default `port + 1000`) serves the same router; public port stays plain HTTP
- Dev mode (no cert paths) auto-generates a self-signed CA + leaf in memory; production loads PEMs from `cluster.tls.{ca_cert,node_cert,node_key}_path`
- TLS reqwest client trusts ONLY the cluster CA (system roots disabled) and presents the node leaf as client identity — i.e. mTLS, not just TLS
- Gossip (chitchat UDP) remains unencrypted: it carries only ring metadata (node IDs + forwarding addresses), not cached data
- `cargo run --bin gen_certs [node_ids...]` writes `./certs/ca.pem` + `./certs/<node>/{cert,key}.pem` for local clusters; the production Dockerfile builds only `--bin ferrocache`, so `gen_certs` never ships in images

**Non-negotiable constraints:**
- Auth is opt-in via `FERROCACHE_AUTH_TOKEN` (M17); cluster mTLS is opt-in via `FERROCACHE_CLUSTER__TLS__ENABLED` (M18). Public-port TLS is out of scope (handled by reverse proxy in production); gossip UDP stays unencrypted
- No UI
- No direct OpenAI/Anthropic API calls inside ferrocache
- Use tokio, not async-std
- Every new module gets unit tests before moving on

**Key decisions:**
- `subtle::ConstantTimeEq` only — never `==`. The crate is 30 lines of public API and exists for exactly this case. The length-check before `ct_eq` is required (the API panics on unequal lengths) and is fine: token length is not secret. The token *value* is.
- `from_fn_with_state(Arc<AuthToken>, ...)` rather than tower-http's `ValidateRequestHeaderLayer` or a hand-rolled `tower::Layer`. Reasoning: the route exemption logic (`/health`, `/metrics`) is the only branch we need, and it's three lines inline; pulling another crate or implementing `Service`/`Layer` boilerplate is pure overhead. The closure-style middleware is the idiomatic axum 0.7 pattern.
- Auth is layered *after* `with_state(state)` so the data handlers continue to receive the original `AppState`, while the middleware gets its own `Arc<AuthToken>` state. The two states are independent; there's no need to thread the token through `AppState`'s state machinery (it's stored there only so `build_router` can read it once).
- Empty-string token treated as disabled. Both `config.auth_token == None` and `config.auth_token == Some("")` skip the middleware install. Reason: env vars in `docker-compose` are easy to accidentally set to `""` (e.g., `FERROCACHE_AUTH_TOKEN: ""`), and silently disabling auth on an empty string is more useful than failing at startup or, worse, requiring an empty bearer token.
- `ClusterRouter::new(auth_token: Option<String>)` — the cluster's inter-node calls go through the same public API surface as external clients. There is no separate "cluster-internal token"; all nodes share the same `FERROCACHE_AUTH_TOKEN`. This keeps the threat model clean: anyone who can present the token can do anything.
- Replaced `tracing::info!(?config, ...)` (Debug-derived) with explicit field-by-field logging. The Debug impl is auto-derived from `#[derive(Debug)]` on `FerrocacheConfig`; trying to skip-Debug a single field would mean either a custom `Debug` impl (boilerplate) or wrapping the whole struct in `secrecy::Secret<...>`. Field-by-field logging is one line longer and provably leak-free.
- Python: `auth_token=None` fallback to `os.environ.get("FERROCACHE_AUTH_TOKEN")` lives *in the client*, not in every wrapper. So `wrap_openai(...)` without an explicit `auth_token=` and without `FERROCACHE_AUTH_TOKEN` set behaves exactly like before; setting the env var or passing the kwarg both light up auth at the SDK boundary. The `_resolve_*` helpers in `middleware.py` weren't extended for auth because the env-fallback already lives one layer down.
- `FerrocacheTools.__init__` mutates `client.auth_token` only when the client doesn't already carry one. Reason: in production the typical wiring is `_build_tools_from_env() → FerrocacheClient(url) → FerrocacheTools(client, ...)` and the *client* picks up the env var automatically, so the explicit `auth_token=` kwarg is redundant. But for tests / direct construction we still want a way to set it on the client retroactively without rebuilding. The "don't overwrite" guard avoids surprise when both are passed.

**Key decisions:**
- Single rustls version across the dep tree. The brief flagged this as risk #1; resolved by switching reqwest to `default-features = false, features = ["json", "rustls-tls"]`. `cargo tree -i rustls` confirms one `rustls v0.23.40` shared by `reqwest`, `axum-server`, `tokio-rustls`, and the direct `rustls` use-site. Using rustls's default crypto-provider (`aws-lc-rs`) means we get FIPS-validated crypto for free with no behavior change.
- Separate internal port for TLS, not SNI/ALPN multiplexing on the public port. The brief's reasoning holds: external clients don't carry client certs (load balancers, Prometheus, Python SDKs), and detecting TLS via SNI inspection adds 200-ish lines of low-value code. The "second listener on +1000" pattern matches Envoy/Linkerd sidecars and is what an operator already expects.
- chitchat KV key stays `api_addr` regardless of TLS state. The brief proposed advertising both `api_addr` and `internal_addr`, but in a homogeneous cluster (per the brief's own constraint: all nodes share the same TLS config) every peer wants the same forwarding addr. Adding a second key buys nothing and creates a "what if they disagree?" failure mode. So `api_addr` semantically becomes "addr peers use to reach me for replication", and TLS-enabled nodes advertise `host:internal_port` under that key; TLS-disabled nodes advertise `host:public_port` as before. Documented in the `ClusterState::new` docstring.
- rcgen 0.13 sign flow: `params.signed_by(&new_keypair, &issuer_cert, &issuer_key)`. The first arg is the *new cert's* keypair (which `impl PublicKeyData`), not the issuer's — easy to get backwards. Smoke-tested by writing `test_generate_node_cert_distinct_from_ca` and `test_build_server_config_smoke` early so this would surface immediately.
- mTLS uses `WebPkiClientVerifier::builder(roots).build()` (not `.allow_unauthenticated()`). Anonymous clients are rejected during the handshake — the auth happens before any HTTP framing, so even `/health` on the internal port requires a client cert. That's intentional: the public port already serves unauthenticated `/health`, and a "TLS-but-anonymous-OK" path on the internal port would be a footgun where someone aims a load-balancer at it and accidentally exposes cluster traffic.
- Crypto provider install is idempotent + deterministic. Brief didn't specify when to install it; chose the latest possible moment (just before `load_or_generate`) and made the call `let _ =` so re-installs are silent. This keeps test ordering simple — every tls test that needs the provider calls `install_default_crypto_provider()` first, and concurrent tests don't race.
- Reqwest client's `tls_built_in_root_certs(false)` is essential. Without it, a peer cert signed by *any* system-trusted CA (Let's Encrypt, the OS root store, anything) would be accepted. With it, only certs signed by the cluster CA verify — which is the entire point of having a private cluster CA.
- The `gen_certs` binary lives at `src/bin/gen_certs.rs` so cargo auto-discovers it; no `[[bin]]` block needed (the brief suggested adding one, but auto-discovery is the idiomatic 2024-edition pattern). The Dockerfile builds only `--bin ferrocache`, so the cert generator never ships in production images — verified by inspection of the Dockerfile's `RUN` line.
- Re-using `app.clone()` for the second listener works because `axum::Router` is `Clone` and shares state via `Arc` internally. So `/metrics` over the internal port reflects the same counters as `/metrics` over the public port — there's exactly one `Metrics` struct in memory, not one-per-listener.

**Deviations:**
- Brief proposed advertising both `api_addr` and `internal_addr` as separate chitchat KVs. Used a single `api_addr` key whose semantic shifts based on local TLS state. Rationale above; documented in code.
- Brief said `subject_alt_names: impl Into<Vec<String>>` on `CertificateParams::new` — confirmed by reading the source (`CertificateParams::new` parses each entry as `IpAddr::from_str` first, falling back to `DnsName`). No need for a custom SAN-builder helper as a result; passing `["node1", "127.0.0.1"]` produces one DnsName + one IpAddress SAN automatically.
- Brief showed `[[bin]] name = "gen_certs"` in Cargo.toml. Skipped — `src/bin/*.rs` is auto-discovered. `cargo run --bin gen_certs` works without the explicit declaration.
- Brief showed an example `KeyPair::generate_for(...)` style. Used the simpler `KeyPair::generate()` (rcgen's default — ECDSA P-256). Both work; the simpler form gives smaller PEM output and is what every rcgen example uses.
- Brief's example `test_node_cert_has_san` parses the cert and verifies SAN contents. Replaced with `test_build_server_config_smoke` + the in-process roundtrip — the roundtrip *implicitly* verifies SANs work because the client connects to `127.0.0.1` and rustls validates the cert's SAN list against the dial-name. A successful handshake = SANs are correct. Lighter than parsing X.509 by hand.
- Brief's compose-file note about commented TLS env vars used `INTERNAL_PORT: "4443"`. Followed exactly, but added a runtime warning (in `main.rs`) when the derived `internal_port` numerically equals the gossip UDP port — they're independent protocols, so it works, but reading "port 4000" in two places in a firewall rule is a footgun.
- Brief asked for two test fixture pairs (`test_mtls_replication_roundtrip`, `test_mtls_rejects_unknown_ca`) plus several smaller ones. Implemented exactly that — both end-to-end tests run an `axum_server::from_tcp_rustls` server in a `tokio::spawn` against an ephemeral 127.0.0.1 port and drive it with reqwest. Roundtrip → 200; bad CA → handshake error.
- Brief proposed `axum_server::bind_rustls(addr, RustlsConfig::from_config(...))` for production. Used exactly that in `main.rs`. Used `from_tcp_rustls(std_listener, ...)` in the tests because they need to capture the OS-assigned ephemeral port before serving (`bind_rustls` doesn't expose the bound socket). Both code paths exercise the same mTLS handshake.

**Open:** Cluster-mode mTLS integration test against actual Docker is missing — the in-process tests cover the rustls handshake and the integration script covers TLS-off; "TLS-on across 3 docker containers via gossip discovery" is the gap. Closing it requires a `docker-compose.tls.yml` overlay that mounts the certs directory and sets the env vars. Skipped for the same reason auth-on integration was skipped in M17: a compose-overlay + parallel script doubles the integration-test maintenance surface and the in-process tests already verify the mTLS handshake end-to-end. The `gen_certs` certs have multi-millennium validity (rcgen's default `not_after = 4096-01-01`) — fine for dev, but `docs/security.md` should call out that production deployments need a real cert lifecycle (CA rotation, leaf rotation, OCSP/CRL distribution) which ferrocache doesn't help with. The internal listener has no graceful-shutdown integration with `axum_server` — `tokio::select!` aborts the spawn task when the public listener exits, but in-flight TLS connections aren't drained. axum-server has a `Handle::shutdown()` API; wiring it through is a nice-to-have. There's no per-cert revocation (CRL/OCSP) — `WebPkiClientVerifier::builder` accepts CRLs, but ferrocache doesn't surface them through config; if a node's key leaks, the only mitigation is rotating the entire CA. The choice of `aws-lc-rs` over `ring` was implicit (rustls's default-features picked it). Both are fine for portfolio purposes; production deployments concerned about FIPS would explicitly opt into `aws-lc-rs`'s FIPS feature, which is out of scope here.
